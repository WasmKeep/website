How it works

Every node runs the same front. Each actor lives on one node at a time, with its own SQLite database, and every database is replicated to one bucket you own. The bucket also holds the leases, so there is no consensus cluster to run.

Kill a node

Three nodes, six actors. Kill a node and watch its lease run out, then another node take its actors from the bucket. The clock runs five times faster than real time; the timings it shows are the defaults and the measured medians, not a live cluster.

    A front on every node

    An app is a front and a set of actor classes, deployed together as one version. The front is a stateless WebAssembly component that serves pages and APIs; any front calls any actor by its address, like room/42, and can batch several calls into one.

    One node per actor, found through the bucket

    The node a request lands on finds the node that holds the actor and forwards the call once, over mutual TLS. A node takes an actor only when the bucket says nobody else holds it, so there is one writer per actor. Idle actors are given up after 30 s by default, and their next event starts them wherever it arrives.

    One SQLite database per actor

    Each actor's database is on its node's disk, written with plain SQL, one event at a time. What each event commits is uploaded to the bucket right after the event; a write made with exec-durable answers only once the bucket holds it.

    The bucket holds the leases

    Each node renews one lease in the bucket. When a node dies, a peer that has seen its heartbeat unchanged writes a fence once 15 s have passed (the 10 s lease plus 5 s of grace), and its actors are free. The wait is what keeps one writer per actor: a node that is only slow must stop acting on its own before anyone else starts.

    When a node dies, with the default timings

    What a caller sees meanwhile is in When a node dies.

    1. 0 s: the node's last heartbeat. A write that reaches another node for one of its actors gets 503 with Retry-After: 1 at once; a read without a body may be kept and answered after the takeover.
    2. 10 s: its lease runs out. Peers stop trusting it over mutual TLS.
    3. 15 to about 21 s: a peer writes the fence; the dead node's actors are free.
    4. Then the restore: the next request for each actor rebuilds its database from the bucket on the node it reaches, and that node answers. Measured end to end: 17.6 s at the median, 23.1 s at p99.
    5. Alarms of the dead node's actors fire elsewhere, late: 20.7 s at the median in the same run. They fire at least once.

    What it does not do

    • No edge network. A cluster runs in one region, next to its bucket; there is no global routing to a nearby location.
    • No instant failover. A dead node's actors wait for its lease and the grace period, then a restore: seconds, measured above.
    • The bucket is a hard dependency. A node cut off from it for 8 s stops serving its actors until it reaches the bucket again.
    • Not a database for queries across actors. Each actor's data is fast to reach through it and slow to query across; keep Postgres for reporting and search.
