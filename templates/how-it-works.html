How it works

Small programs. Shared recovery.

Keep each room, user or device together on one server. If that server fails, another can rebuild it from your bucket. You run the servers and a bucket, without a separate coordination service.

Take a server offline. Follow the recovery.

Tap a node to stop it, or tap an actor to explore its actions. The illustration restores actors across surviving servers after a safety wait. If all servers stop, requests fail until you restart one.

This is a model, not a live cluster. It starts with three nodes and six actors. The lifecycle clock runs five times faster; packet hops are slowed so you can follow them.

Less coordination to build yourself

Your app handles the request. WasmKeep finds its actor, keeps writes in order and stores recovery data in your bucket.

Concepts and Running a cluster have the details and the limits.

Reach your app through any server

An app is a front and a set of actor classes, deployed together as one version.

The front is a stateless WebAssembly component that serves pages and APIs; any front calls any actor by its address, like room/42, and can batch several calls into one.

Let WasmKeep find the right actor

The node a request lands on finds the node that holds the actor and forwards the call once, over mutual TLS.

A node takes an actor only when the bucket says nobody else holds it, so there is one writer per actor. Idle actors are given up after 30 s by default, and their next event starts them wherever it arrives.

Keep each actor’s data together

Each actor's database is on its node's disk, written with plain SQL, one event at a time.

What each event commits is uploaded to the bucket right after the event; a write made with exec-durable answers only once the bucket holds it. Plain writes may lose the latest events on a crash.

What saved means: choose a crash moment and compare plain and durable writes.

Wait safely before taking over

Each node renews one lease in the bucket. When a node dies, a peer that has seen its heartbeat unchanged writes a fence once 15 s have passed (the 10 s lease plus 5 s of grace), and its actors are free.

The wait is what keeps one writer per actor: a node that is only slow must stop acting on its own before anyone else starts.

A crash starts a recovery, not a reset

Recovery takes seconds, and requests may fail while it happens. The default sequence is below. Read When a node dies.

  1. 0 s: the node's last heartbeat. A write that reaches another node for one of its actors can get 503 with Retry-After: 1; an eligible read without a body may be kept and answered after takeover. A request already forwarded to a silent node can instead time out with 504. A failed response does not prove the write never ran.
  2. 10 s: its lease runs out. Peers stop trusting it over mutual TLS.
  3. 15 to about 21 s: a peer writes the fence; the dead node's actors are free.
  4. Then the restore: the next request for each actor rebuilds its database from the bucket on the node it reaches, and that node answers. Measured end to end: 17.4 s at the median, 22.5 s at p99 and 29.0 s at worst in the 0.4.2 release candidate's 2-hour soak; 33.7 s at worst over 239 kills in the 12-hour soak.
  5. Alarms of the dead node's actors fire elsewhere, late: 20.0 s at the median in the same run. They fire at least once. How we measured.

Plan for the limits

  • No edge network. A cluster runs in one region, next to its bucket; there is no global routing to a nearby location.
  • No instant failover. A dead node's actors wait for its lease and the grace period, then a restore: seconds, measured above.
  • The bucket is a hard dependency. A node cut off from it for 8 s stops serving its actors until it reaches the bucket again.
  • Not a database for queries across actors. Each actor's data is fast to reach through it and slow to query across; keep Postgres for reporting and search.

This site's source

This site is built as a WasmKeep app (source): a Rust front that serves the pages, built with Zola and embedded at build time, and the language wall's API. Each wall counter is an actor named wall in its language’s class, reached only by the front. The wall-room/main actor holds the WebSockets that broadcast updates.
