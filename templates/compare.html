WasmKeep and the alternatives

Several good tools give each piece of state its own small home. They differ on what you write it in, where the state lives, when a write counts as done, and who runs it. Here is each one as its own pages describe it, and when to pick it instead.

Read on each project's own site or repository on 2026-11-14; sources at the end. A cell says "not stated" where the pages we read do not say. Corrections are welcome as an issue.

Side by side

Project Model and languages Where state lives When a write is acknowledged Run it yourself Licence Maturity
WasmKeep Actors, one per name, one event at a time. Any WASI 0.2 component: SDKs for Rust, TypeScript, Python, C, Zig, Go (TinyGo); standard Go, D, MoonBit experimental. One SQLite database per actor on its node's disk, replicated to your S3-compatible bucket. exec-durable: once the bucket holds it. Plain exec: once committed locally, uploaded right after the event. Yes, only: one binary per node, nodes share a bucket. Apache-2.0 Pre-alpha, 0.4.1 (pre-release).
Cloudflare Durable Objects One object per id, on Workers. JavaScript, TypeScript and Python; other languages through a shim to a JavaScript class. A SQLite database embedded in each object, on Cloudflare's network; 10 GB per object on Workers Paid. Writes go to a buffer flushed to disk; an output gate holds outgoing messages until earlier writes are confirmed flushed. The platform is Cloudflare's. workerd, its open-source runtime, serves Durable Objects locally, with a cluster mode marked experimental. Managed service; workerd is Apache-2.0. Generally available since 2021; SQLite storage GA in April 2025.
celld Wrangler bundles on V8 (Workers, Durable Objects, KV, Queues, D1, R2, Workflows) from your wrangler.json. Each object a "cell" with its own SQLite database; long-term state in your S3, GCS or Azure bucket. One node: once the bucket has it. Two or more: once one or two other nodes hold it on disk; the bucket upload follows. Yes: a daemon on your machines. Apache-2.0 v0.6.3, which its docs call a beta release. Pull requests disabled; patches by email under a CLA.
Rivet Actors: long-lived processes with in-memory state, SQLite, WebSockets and scheduling. RivetKit for TypeScript and Rust; Python and Swift experimental. Its site says each actor's data lives in a bucket you own; its state docs also mention a durable volume. "every committed write is replicated before it is acknowledged"; in-memory vars are never persisted. Yes: Docker, Kubernetes or a VM. Apache-2.0 v3.1.1 (November 2026).
Golem Durable agents as WebAssembly components: Rust, TypeScript, Scala and MoonBit. An append-only oplog per agent, on Redis, PostgreSQL or SQLite, archived to S3 or a filesystem; recovery replays it. Not stated on the pages we read. Yes: a single binary, your infrastructure, or Golem Cloud. Business Source License 1.1, Apache-2.0 four years after each release. v1.6.3 (November 2026).
Microsoft Orleans Virtual actors ("grains") in .NET. A storage provider you choose: ADO.NET databases, Azure Storage, Cosmos DB, DynamoDB, Redis and others. When WriteStateAsync completes; a storage failure throws from it. State is not persisted until you call it. Yes: wherever .NET runs, including Kubernetes. MIT Used at Microsoft in Azure, Xbox and others; v10.4.2.
Dapr actors Turn-based actors behind a sidecar. Actor SDKs for .NET, Python, Java, Go, PHP and JavaScript. One transactional state store you configure for actors. Not stated on the pages we read. Yes: open source. Apache-2.0 A CNCF graduated project; v1.19.1.
Temporal Durable execution of workflows. SDKs for Go, Java, Python, TypeScript, .NET, Ruby, PHP and Rust. Each workflow's event history, in the Temporal Service's database: Cassandra, PostgreSQL or MySQL. Not stated as such; the event history is the source of truth that recovery replays. Yes: the Temporal Service is open source. MIT v1.32.2 (November 2026).
Restate Durable execution; Virtual Objects with a single writer per key. SDKs for TypeScript, Java, Kotlin, Python, Go, Rust and Ruby. The Restate Server's log, on disk and replicated, with RocksDB for state; snapshots in S3 for clusters. In a cluster, a majority must accept new log entries; the exact point of the answer is not stated. Yes: a single binary, one node or a cluster. Server: Business Source License 1.1, Apache-2.0 after four years. SDKs: MIT. v1.8.1 (November 2026).

Pick them instead when

WasmKeep is young. Each of these is the better choice for someone; this is when it is likely to be you.

  • Cloudflare Durable Objects

    You want a managed global network, years of production at Cloudflare's scale, a mature JavaScript ecosystem and no servers to run. At small and medium scale it is likely as cheap or cheaper too: see Cost.

  • celld

    You already have Workers code and want it on your own machines as it is, with the Workers platform pieces (KV, Queues, D1, R2) beside it. WasmKeep has its own API and no Workers compatibility.

  • Rivet

    Your backend is TypeScript and you want actors inside it, on Node.js or Bun.

  • Golem

    You want durable execution of a whole agent, replaying its interactions after a failure, rather than a database per actor that you write to yourself.

  • Orleans

    Your team writes .NET and your state belongs in a database you already run. Orleans is mature, and Microsoft runs it in its own services.

  • Dapr actors

    You run Kubernetes and want actors beside Dapr's other building blocks, from many languages, on a state store you already have.

  • Temporal

    Your problem is long-running workflows across services (orders, payments, provisioning) more than many small pieces of state.

  • Restate

    You want durable handlers and per-key state in front of services you already have, in your existing language, with one server to run.

Where WasmKeep fits

Pick WasmKeep when you want the one-object-per-thing model on servers you own, in a compiled language or several, with each actor's data as SQLite files and a documented replication format in your own bucket, and with every durable write in that bucket before it is acknowledged. Accept, today, that it is pre-alpha, runs in one region per cluster, and takes seconds to fail over.

The documentation compares it in more depth, with measurements, with Cloudflare Workers and with celld.
