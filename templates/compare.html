WasmKeep and the alternatives

Several good tools give each piece of state its own small home. WasmKeep's case is a combination: your servers and your bucket, languages whose toolchains build WASI 0.2 components for WasmKeep's interfaces, and acknowledged durable writes (exec-durable) that survive their node. SDK features vary by language; plain writes may lose the latest events on a crash. Here is when to pick it, how the others describe themselves, and when to pick them instead.

Read on each project's own site or repository on 2026-11-14; sources at the end. A cell says "not stated" where the pages we read do not say. Corrections are welcome as an issue.

Pick WasmKeep when

  • {{}}You want it on your servers, with your bucket

    One binary per node; the nodes share any S3-compatible bucket, which holds the leases and every actor's history. Soaked with nodes killed under load against Cloudflare R2 and OVHcloud Object Storage (benchmarks).

  • {{}}Your code is not JavaScript

    Actors are standard WASI 0.2 components run by Wasmtime, with no JavaScript in between. On one workstation the Rust, Zig and C counters used 104, 107 and 110 µs of server CPU per request (every language).

  • {{}}A write must survive its node

    exec-durable answers only once the bucket holds the write, on one node or many. 12 hours, 239 kills on three VPS: 2,306,192 acknowledged durable writes, none lost or applied twice (CSV).

  • {{}}You want to read the evidence

    Apache-2.0, pull requests welcome under a CLA, and every published number backed by a CSV in bench/results, including runs that failed a check.

Accept, today, that it is pre-alpha, runs in one region per cluster, and takes seconds to fail over: 17.4 s at the median and 29.0 s at worst in the 0.4.2 release candidate's 2-hour soak, 33.7 s at worst in the 12-hour soak.

Pick them instead when

WasmKeep is young. Each of these is the better choice for someone; this is when it is likely to be you.

More on Durable Objects and celld below, with measurements.

  • Cloudflare Durable Objects

    You want a managed global network, years of production at Cloudflare's scale, a mature JavaScript ecosystem and no servers to run. At small and medium scale it is likely as cheap or cheaper too: see Cost.

  • celld

    You already have Workers code and want it on your own machines as it is, with the Workers platform pieces (KV, Queues, D1, R2) beside it. WasmKeep has its own API and no Workers compatibility.

  • Rivet

    Your backend is TypeScript and you want actors inside it, on Node.js or Bun.

  • Golem

    You want durable execution of a whole agent, replaying its interactions after a failure, rather than a database per actor that you write to yourself.

  • Orleans

    Your team writes .NET and your state belongs in a database you already run. Orleans is mature, and Microsoft runs it in its own services.

  • Dapr actors

    You run Kubernetes and want actors beside Dapr's other building blocks, from many languages, on a state store you already have.

  • Temporal

    Your problem is long-running workflows across services (orders, payments, provisioning) more than many small pieces of state.

  • Restate

    You want durable handlers and per-key state in front of services you already have, in your existing language, with one server to run.

In detail: Cloudflare Durable Objects

The closest programming model: one addressable object per name, one event at a time, its own storage, alarms and WebSockets. Two things carry the name: workerd, the open-source runtime, and Cloudflare Workers, the hosted platform. The numbers below compare runtimes; much of what makes Workers strong is the platform.

Pick Durable Objects for a managed global network, a mature JavaScript ecosystem and no servers to run; pick WasmKeep for durable actors on your servers, in a compiled language, with the data in your bucket. WasmKeep and Cloudflare Workers has the full comparison.

In detail: celld

The same idea, built on the Workers API: Durable Object-style actors on your own servers, each with its own SQLite database, replicated to a bucket. Both ran the same counter on the same machine and the same local bucket. celld v0.6.3, five runs of each, medians with the lowest and highest in brackets.
