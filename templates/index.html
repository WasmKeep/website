Stateful actors in any language, on servers you own.

WasmKeep runs one small program per room, user, tenant or device. Each is a WebAssembly component with its own SQLite database, handling one event at a time, replicated to a bucket you own.

{{}}Pre-alpha, {{ config.extra.release }}. Soaked with nodes killed under load, but not yet carrying real users' traffic. Do not trust it with data you care about yet. What works today.

Install on Linux (x86_64 or aarch64, glibc 2.28 or newer)

v={{ config.extra.release }}
f=wasmkeep-$v-$(uname -m)-unknown-linux-gnu.tar.gz
curl -fsSLO "https://github.com/WasmKeep/wasmkeep/releases/download/v$v/$f"
tar xzf "$f" && sudo install -m 755 "${f%.tar.gz}/wasmkeep" /usr/local/bin/wasmkeep

Every release file is signed: check a download before you trust it. Or run the image ghcr.io/wasmkeep/wasmkeep:{{ config.extra.release }}.

Measured, with the raw files

Every number here comes from a CSV the benchmark scripts wrote, linked below. None comes from memory, and what was not measured is said.

Benchmarks has the method, the hardware and what each run does not test.

  • 0acknowledged durable writes lost, over 2,306,192 of them and 239 node kills in 12 hours on three VPS1
  • 17.6 smedian until a dead node's actors are writable again elsewhere; 23.1 s at p992
  • 81 msmedian durable write as a client sees it, next to the bucket, under load2
  • 61 µsmedian read of a resident Rust actor; 250 KB of memory per resident actor3
  1. Three OVHcloud VPS next to OVHcloud Object Storage, a node killed every 3 minutes for 12 hours, every acknowledged write read back: 2026-11-12-b849bfe-soak-ovh-bhs-3vps-12h.csv. Durable writes only: plain writes, which answer before the upload, may be lost with their node, and a 3-hour run lost 2 (648c2d1).
  2. The 0.4.1 release candidate, the same three VPS, 2 hours, 39 kills, 1,225 actors taken over, worst 27.1 s: 2026-11-14-0bf0547-soak-ovh-bhs-3vps-2h-0.4.1-rc.csv. Durable write p99: 1.02 s.
  3. A 16-core workstation, data on tmpfs, eight clients: 2026-11-06-351ea57.csv. The machine changes the answer; read it as an order of magnitude.

What people build with actors

Many small, independent pieces of state, each with a modest stream of events, often with WebSockets or timers. Keep Postgres for what spans everything.

Use cases compares each one with stateless servers, Postgres and Valkey.

  • {{}}Rooms and presence

    One actor per room: its sockets, members and the order of its messages in one place. Sockets stay open while it sleeps.

    examples/chat-room

  • {{}}Rate limits and quotas

    One actor per API key or tenant handles one event at a time, so the count is exact without a lock.

    examples/rate-limiter

  • {{}}Monitors and reminders

    An alarm on the actor, delivered at least once, also when its node dies. No cron, job table or lock.

    examples/watch

  • {{}}AI agents

    A conversation is state plus a loop: its history in SQLite, a model over HTTP, a reminder tool on an alarm.

    examples/agent

  • {{}}Workflows

    Durable steps as a library on an ordinary actor, in Rust and TypeScript, with clients in the other SDKs.

    examples/workflows

  • {{}}An app with a front

    A stateless front serves pages and APIs and calls the actors, like this site does.

    examples/todo-front
