How it compares, and when to pick something else

  • {{}}Fewer services to run

    One binary per node; nodes share a bucket you own. Soaked against Cloudflare R2 and OVHcloud Object Storage with nodes killed under load.

  • {{}}Choose a language that fits

    Use Rust, TypeScript, Python and more. SDK support varies by language. In one workstation test, Rust, Zig and C used similar CPU time per request.3

  • {{}}Keep confirmed writes after a crash

    A write made with exec-durable answers after the bucket holds it, so it survives its node: no acknowledged durable writes lost over 239 kills in 12 hours.1 Plain writes may lose the latest events on a crash.

  • {{}}Apache-2.0, developed in the open

    Inspect the code and the published results, including tests that failed. Contributions are welcome under a CLA.

Recovery you can inspect

In crash tests, confirmed durable writes survived the loss of their server. Recovery took seconds. These results describe tested workloads, not a guarantee for your app.

How we measured: machines, workloads and raw results.

  • 0acknowledged durable writes lost, over 2,306,192 of them and 239 node kills in 12 hours on three VPS1
  • 17.4 smedian until a dead node's actors are writable again elsewhere; 22.5 s at p99, 29.0 s at worst in that 2-hour run2
  • 81 msmedian durable write as a client sees it, next to the bucket, under load2
  • 61 µsmedian read of a resident Rust actor; 250 KB of memory per resident actor3
How we measured

Benchmark methods and results. Each figure above refers to a test below.

  1. Three OVHcloud VPS next to OVHcloud Object Storage, a node killed every 3 minutes for 12 hours, every acknowledged write read back: Raw test results. Worst time to writable again in that run: 33.7 s. Durable writes only: plain writes, which answer before the upload, may be lost with their node, and a 3-hour run lost 2 (Raw test results). The files' write errors are attempts that got no acknowledgement (an error or no answer, as while a node is down); only acknowledged writes are checked and counted.
  2. The 0.4.2 release candidate, the same three VPS, 2 hours, 39 kills, 1,264 actors taken over, worst 29.0 s: Raw test results. Durable write p99: 1.02 s.
  3. A 16-core workstation, data on tmpfs, eight clients: Raw test results. The machine changes the answer; read it as an order of magnitude.

Keep your data in your bucket

Choose where your app stores its recovery data. Your servers share an S3-compatible bucket; WasmKeep checks that it supports the writes needed to keep a single owner for each actor.

Buckets lists what WasmKeep needs from one, and how to check yours.

{{}}Soaked with nodes killed
Cloudflare R2, OVHcloud Object Storage
{{}}Used in tests and benchmarks
MinIO and moto, run locally
{{}}Documents both conditional writes; not tested by us yet
AWS S3 (its conditional writes)
{{}}Anything else S3-compatible
Run wasmkeep cluster diagnose against it first; a node refuses a bucket that ignores conditional writes.
{{}}Not supported yet
Google Cloud Storage and Azure Blob Storage: WasmKeep speaks only the S3 API today, and has no native backend for either yet.

What you can build

Build around a room, a customer or a device. Keep its activity and data together, while other actors work independently. Use a shared database for reporting across the whole app.

Use cases compares each one with stateless servers, Postgres and Valkey.

  • {{}}Rooms and presence

    One actor per room: its sockets, members and the order of its messages in one place. Sockets stay open while it sleeps.

    Explore a chat room

  • {{}}Rate limits and quotas

    One actor per API key or tenant handles one event at a time, so the count is exact without a lock.

    Build a rate limiter

  • {{}}Monitors and reminders

    An alarm on the actor, delivered at least once, also when its node dies. No cron, job table or lock.

    Build a monitor

  • {{}}AI agents

    A conversation is state plus a loop: its history in SQLite, a model over HTTP, a reminder tool on an alarm.

    Explore an agent

  • {{}}Workflows

    Durable steps as a library on an ordinary actor, in Rust and TypeScript, with clients in the other SDKs.

    Explore workflows

  • {{}}An app with a front

    A stateless front serves pages and APIs and calls the actors, as this site's source does.
