If the node crashes here

      “Lost” means absent from the restored history in this example. “Not run” means the crash came before that write. A reply is what this example's caller has received.

      What each promise covers

      The released modes below describe WasmKeep 0.4.2. The planned batching note describes a proposal, not a setting in that release or this timeline.

      Plain exec

      Commits locally and returns. The handler can reply before the upload, which follows the event. In 0.4.2, the actor waits for that upload before running its next event. A crash before upload can lose the write, even after a reply; a later increment can return the same counter value again.

      exec-durable

      Returns successfully only after the bucket holds the write and every earlier write of that actor, with the upload completed while the node still holds the actor. This example's handler waits for that success before replying. A received durable acknowledgement survives loss of the node.

      Batched plain writes planned for 0.5.0, opt-in

      ADR 0034 proposes letting later events see local writes while uploads are pending. A crash can lose the whole unreplicated window, including several writes already answered. Strict behavior stays the default; durable operations still wait for the bucket. Batch size and loss limits are not specified by this note.

      No reply does not mean no write

      Crash after upload but before the reply: the write survives, but the caller does not know that. Make retries safe to repeat. An upload still in flight at a crash can also have an uncertain outcome.

      This model selects a clean boundary: an upload is either not started or completed under a valid hold. It omits upload races, errors and the wait for takeover. Restore is from the bucket, not the failed node's disk. On a single node without a bucket, exec-durable instead waits for a local fsync.
