What works today

The capabilities below are available in WasmKeep {{ config.extra.release }}. It is pre-alpha, tested and measured, but not yet carrying real users’ traffic.

  • {{}}A SQLite database per actor

    Each actor owns its state in its own database, queried with plain SQL, and handles one event at a time, in arrival order: two requests to the same actor never interleave.

    Concepts

  • {{}}Durable writes, acknowledged once in the bucket

    A write made with exec-durable answers only once the bucket holds it, so it survives its node. A plain exec answers sooner and is uploaded right after the event, so it can be lost with its node in that moment.

    The replication contract

  • {{}}Failover without a consensus cluster

    The bucket holds the node leases, the owners and each actor's history. A dead node's actors are free 15 to about 21 s after its last heartbeat, then restored elsewhere.

    When a node dies

  • {{}}Your S3-compatible bucket

    Soaked on Cloudflare R2 and OVHcloud Object Storage. Any other S3-compatible store: check it with wasmkeep cluster diagnose. Google Cloud Storage and Azure Blob Storage are not supported yet.

    Buckets

  • {{}}Hibernation

    Idle actors leave memory. Their next event wakes them with their data, pending alarm and open WebSockets.

    Life cycle

  • {{}}Languages that build WASI 0.2 components

    Languages whose toolchains build WASI 0.2 components for WasmKeep's interfaces can write actors. SDK features vary by language. Rust, TypeScript, Python, C, Zig and Go (TinyGo) have SDKs and pass the same tests; standard Go, D, MoonBit and C# are experimental.

    Languages

  • {{}}Apps with a front

    A stateless front serves pages and APIs and calls the app's actors, several in one batch, deployed with its classes as one version.

    The project file

  • {{}}Alarms and WebSockets

    Alarms fire at least once, also when their node dies. WebSockets stay open while their actor sleeps.

    Concepts

  • {{}}A sandbox per actor, mutual TLS between nodes

    CPU, memory and SQL limits per actor, no filesystem, no data but its own. Every actor of a node shares one process: not yet a boundary for hostile tenants.

    Security model

  • {{}}Built to operate

    cluster status reads a cluster from the bucket alone, cluster drain empties a node, secrets keeps an app's secrets sealed in the bucket.

    Running a cluster

  • {{}}Signed releases, Apache-2.0

    One binary per node. Every release file has a Sigstore bundle and each binary a CycloneDX SBOM, built and signed by CI.

Limits and planned work

Weeks of real traffic, a run against AWS S3, an independent security audit, and a sandbox tier for tenants who do not trust each other. Export and online backup are planned for 0.5.0; rebalancing at wake-up is planned for 0.6.0. Neither is available in 0.4.2. Follow the roadmap.
